## 二、Luraph v15.1 的内部结构（四层，全部定位）

```
① 字符载荷   212,485 字符，每 5 个字符为一格，每位 = 字符码 − 32（0~84，85 进制）
      ↓ 解码（源码 ZW 中的 85³ / 85² / 85⁴ 权重公式）
② 源 buffer  135,710 字节密文（熵 8.00 bit/byte）
      ↓ XOR：plain_u32 = readu32(src, off) ^ x ^ nW[P]      【已实测验证】
③ 目标 buffer  32 位字（全部 ≥ 809,472，非小整数）
      ↓ keyed 字节生成器（sW 中的 (z*M+K)%256 链）           【未读透】
④ 最终指令流  含操作码 0~84
```

### 已确证的数据（都有实测支撑）

- **指令格数**：212,485 ÷ 5 = **42,497**
- **主密钥**：`x = 2981212593`（2500 条采样里完全恒定）
- **偏移序列**：6, 10, 14, … 步长 4
- **keystream**：`nW[P]`，每块不同，来自 VM 的 `nW` 数组（255 项）
- **XOR 公式**：用目标缓冲区直接读回的值与离线计算**逐一吻合**

## 四、项目决策（2026-10-25 用户拍板）

**不再往「读懂 Luraph」方向投入。**

理由：脚本**能跑、能改参数**，使用价值已经达成；看懂本身不产生额外价值。

- 想改数值 → 直接改混淆层里的数字/字符串，立即生效
- 想加功能 → **不要塞进混淆体**，另写脚本用 hook 挂在旁边
- 只有「复制核心逻辑」或「绕过校验」才需要懂内部，而那两种场景用**运行时 hook 比静态反编译快得多**

## 六、踩过的坑（勿再犯）

- `buffer` / `table` 是 **readonly**，`buffer.xxx = wrapper` 直接报错；只能源码级替换绑定或纯插入探针
- **代理表方案会死循环卡死设备**（VM 用 rawget/rawset 绕过元表）——禁用
- paste.rs 单次上限 ~80KB，超了 500；uguu.se 能收 632KB 但文件很快被清（几分钟就 404）
- 大输出不要直接打印，先落文件再分析
